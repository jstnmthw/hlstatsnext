# 0010. Development infrastructure credentials are Compose defaults, not a root env file

- Status: Accepted
- Date: 2026-10-18

## Context

`docker-compose.yml` sits at the repository root and, following Compose's own convention, read a root `.env` for `${VAR}` interpolation. Turborepo's convention points the other way: `turbo run` loads no env file, so each package loads its own, which the apps already do through dotenv and Next.js. The root file therefore served Compose alone, and its template had drifted. Of its 22 variables, five were read by nothing (`USER_ID`, `GROUP_ID`, `DB_HOST`, `DB_PORT`, `DB_CHARSET`), six were app-side pool settings Compose never forwarded, and one duplicated the `name:` already in the Compose file. The development database password was also written in five files that had to agree: the root file provisioned the MySQL user, and web, api, daemon and db each connected with it. The templates disagreed (`hlstatsnext`, `CHANGE_ME_DB_PASS`, `changeme`, `CHANGE_ME`), so copying every template as the README instructed produced a stack in which nothing could connect. The test stack in `docker-compose.test.yml` and CI already used fixed credentials with no env file.

## Decision

The development Compose stack takes its credentials from the `${VAR:-default}` fallbacks in `docker-compose.yml`, there is no root `.env`, and the app templates ship with the same values so a fresh clone connects without edits. Only `ENCRYPTION_KEY` and `BETTER_AUTH_SECRET` are generated by the developer. Production keeps its own env file beside the production Compose file, as `docs/DEPLOYMENT.md` describes.

## Options considered

- **Compose fallbacks as the source of truth, no root file.** Chosen. Matches the test stack and CI, removes the fifth copy of the password, and `${VAR:-default}` keeps a shell export or `--env-file` as the override for anyone who needs one. Credentials for a localhost-bound development stack are not secrets.
- **Keep the root `.env` but trim it to the nine Compose variables.** Rejected. An honest file, but the password still lives in five places and the template mismatch remains unless the defaults are aligned anyway, at which point the file adds nothing.
- **Move the Compose stack into `docker/` so its `.env` lives there.** Rejected. Satisfies the letter of the Turborepo guidance but changes every bind-mount path, the build context and the `docker:*` scripts for a cosmetic gain.
- **One env file shared by the daemon container and the host apps through `env_file:`.** Rejected. Host processes reach the database at `localhost` and the container at `db`, so one `DATABASE_URL` cannot serve both.

## Consequences

- Fresh setup is: copy the four app templates, generate two secrets, `pnpm docker:up`. The root copy step is gone from `README.md`, `DEVELOPMENT.md` and `INSTALLATION.md`.
- MySQL and AMQP are published on `127.0.0.1` only, because the credentials are now public. The UDP log port stays open for game servers.
- MySQL and RabbitMQ create users only on the first start of an empty volume. A developer whose volume was provisioned under the old root `.env` either keeps that file (Compose still reads it if present) or runs `docker compose down -v` once and loses the development data.
- `RABBITMQ_USER`, `RABBITMQ_PASSWORD` and `RABBITMQ_VHOST` leave the daemon template; the daemon reads only `RABBITMQ_URL`.
- A new Compose variable gets its fallback in `docker-compose.yml` and a row in `INSTALLATION.md`, not a root template.
